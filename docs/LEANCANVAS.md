## 1. 문제 (Problem) ✅

| # | 문제 | 누가 겪나 | 근거 |
|---|---|---|---|
| 1 | 공지·참석·카풀·정산이 카톡방에 흩어져 주최자가 매번 공지 쓰고, 인원 세고, N빵을 계산한다 | 주최자(총무 민수) | PRD 1장 |
| 2 | 정보가 채팅에 묻혀 참여자가 참석 현황·카풀·입금 상태를 찾기 어렵다 | 참여자(게스트 지현) | PRD 1장 |
| 3 | 앱 설치·가입을 요구하면 응답을 포기한다 — 링크 눌러 3탭 안에 끝내고 싶다 | 참여자 | PRD 페르소나 |

**기존 대안**: 카카오톡 공지·투표, 구글폼, 엑셀, 토스 정산 — 각각 한 가지만 해결하고 연결되지 않는다.

## 2. 고객 세그먼트 (Customer Segments) ✅

- **얼리어답터**: 교회 소그룹/셀 리더, 수영·헬스 동호회 총무, 친구 모임 주최자 (월 1~4회 모임)
- **주최자**와 **참여자**는 다른 사용자다. 주최자가 도입을 결정하고, 참여자가 따라 들어온다.
  - 주최자: 로그인(카카오)하여 관리 → 핵심 사용자, 과금 후보 🟡
  - 참여자: 비로그인, 무료 → 새 주최자로 전환되는 바이럴 경로 🟡

## 3. 가치 제안 (Unique Value Proposition) ✅

> **"링크 하나로 모임 운영 끝."**

- 주최자: 공지·참석·카풀·정산을 **한 화면**에서 관리, 반복 수작업 제거
- 참여자: **가입·설치 없이** 링크 → 이름 → 응답
- 상위 개념(High-level concept): 모임 총무를 위한 원링크 올인원

## 4. 해결책 (Solution) ✅

| 문제 | 해결책 | MVP 기능 (PRD 2장) |
|---|---|---|
| 1 | 한 이벤트에 4가지 기능을 묶음 | 이벤트·공지·공유 링크 / RSVP·명단 / 카풀 / 정산 |
| 2 | 링크 한 장에 현황 집약, 정원·대기·좌석을 자동 처리 | 정원 초과 시 대기 FIFO 승격, 카풀 좌석 자동 차감, 내 부담금·입금 상태 화면 |
| 3 | 참여자 비로그인 | 링크 + 이름 → `participant_token`(httpOnly 쿠키), 응답 3탭 이내 |

**MVP 제외(Out)**: 알림톡 자동발송, 반복 모임, 그룹 관리, 지도 경로, 송금 연동, 회비 자동 납부, admin 대시보드, 다중 결제자 정산

## 5. 경쟁우위 (Unfair Advantage) 🟡

> PRD에는 명시된 항목이 없다. 아래는 현재 구조에서 도출한 **후보**이며, 린 캔버스 정의상 "쉽게 복사·구매할 수 없는 것"과는 거리가 있다.

| 후보 | 설명 | 지속성 |
|---|---|---|
| 참여자 가입 불필요 모델 | 링크+이름만으로 진입, 토큰은 해시로만 저장 | 낮음 — 경쟁사도 따라 할 수 있음 |
| 모임 특화 규칙의 DB 강제 | 정원 FIFO 대기, 카풀 좌석 초과 방지, 정산 확정 스냅샷, 이벤트 상태 가드 | 낮음~중간 — 운영 데이터가 쌓이면 규칙 보정에 유리 |
| 교회·동호회 네트워크 | 초기 사용자·피드백을 직접 확보할 수 있는 접점 | 중간 — 개인 네트워크에 의존 |

**솔직한 평가**: 현재는 "실행 속도와 도메인 이해"가 우위이고, 구조적 해자는 없다. 데이터(모임 이력)와 반복 사용 습관이 해자가 되려면 **재생성률**이 핵심이다.

## 6. 수익 흐름 (Revenue Stream) 🟡

> PRD는 수익 모델을 다루지 않는다. MVP 단계에서는 **무료로 사용자·재사용 데이터를 확보**하고, 아래 후보 중 베타 데이터로 선택한다.

| 후보 | 조건 | 위험 |
|---|---|---|
| 프리미엄 주최자 구독 | 반복 모임, 모임(그룹) 관리, 정산 리포트 등 Post-MVP 기능이 생긴 뒤 | 총무가 무료 대안(카톡+엑셀)에서 이탈할 만큼 가치가 있는가 |
| 알림톡 발송 비용 전가 | 알림톡 자동 발송 도입 시 | 변동비 대비 단가 설정 |
| 송금 연동 수수료 | 토스/카카오페이 연동 시 | **결제·송금 관련 법적 검토 필수**, MVP 범위 밖 |

가격·전환율은 근거 데이터가 없어 정하지 않는다.

## 7. 비용 구조 (Cost Structure) 🟡

| 구분 | 항목 | 비고 |
|---|---|---|
| 개발 | 1인 개발 약 7~8주 ✅ | ROADMAP 추정 |
| 인프라 | Supabase(DB·Auth), 호스팅(Vercel 예정), 도메인 | 요금제는 사용량 기준으로 확인 필요 |
| 인증 | 카카오 OAuth | 비즈앱·이메일 동의항목 설정에 시간이 걸릴 수 있음(일정 리스크) |
| 변동 | 알림톡 발송(Post-MVP), 트래픽 증가분 | 이용자 증가 시 |
| 운영 | 베타 모임 지원, 피드백 대응 | 개발과 병행 |

## 8. 주요 지표 (Key Metrics)

| 지표 | 목표 | 단계 | 근거 |
|---|---|---|---|
| 이벤트당 응답률 | ≥ 80% | 베타 | ✅ PRD 8장 |
| 주최자 재생성률(이벤트 2회 이상) | ≥ 40% | 베타 종료 후 측정 | ✅ PRD 8장 |
| 참여자 응답 완료 시간 | 평균 30초 이내 | 베타 | ✅ PRD 8장 |
| 응답 후 정산 완료율 | 추후 정의 | 베타 | 🟡 제안 |
| 주 단위 신규 이벤트 수 | 추후 정의 | 베타 | 🟡 제안 |

> 재생성률 같은 반복 지표는 첫 모임 이후 시간이 지나야 측정된다. 베타를 **개발과 병행**하는 이유다.

## 9. 채널 (Channels) 🟡

1. **카톡방 공유 링크**: 주최자가 이벤트 링크를 단톡방에 올리는 것이 곧 배포다. 링크 미리보기(OG 메타, ROADMAP Phase 5 P1)가 클릭률을 좌우한다.
2. **참여자 → 새 주최자 전환**: 참여자 화면에 "나도 모임 만들기"를 노출한다(제안, PRD 미반영).
3. **베타 직접 도입**: 교회 모임 2~3팀에 직접 도입하고 피드백을 수집한다 ✅(PRD 8장).
4. **입소문**: 같은 교회·동호회 내 다른 모임으로 확산.

## 먼저 검증할 가설 (Riskiest Assumptions)

| 순위 | 가설 | 틀리면 | 검증 방법 |
|---|---|---|---|
| 1 | 총무가 **이미 쓰는 카톡방 대신** 외부 링크를 쓸 것이다 | 채널과 가치 제안이 모두 무너짐 | 베타 2~3팀에서 첫 이벤트를 실제로 이 서비스로 운영하는지 관찰 |
| 2 | 참여자가 **가입 없이** 링크만으로 80% 이상 응답한다 | 핵심 차별점(가입 불필요)의 효과가 입증 안 됨 | 이벤트별 응답률, 카톡 인앱 브라우저 쿠키 유지율 측정 |
| 3 | 총무가 **돈을 낼 만큼** 반복해서 쓴다 | 수익 모델이 성립하지 않음 | 재생성률과 "다음 모임에도 쓸 것인가" 인터뷰 |

## PRD와의 대응

| 캔버스 칸 | PRD 근거 |
|---|---|
| 1 문제 | 1장 문제 정의, 페르소나 |
| 2 고객 세그먼트 | 1장 1차 타깃 |
| 3 가치 제안 | 상단 한 줄 요약, 차별점 |
| 4 해결책 | 2장 MVP 범위, 5장 기능 요구사항 |
| 8 주요 지표 | 8장 성공 지표 |
| 5, 6, 7, 9 | **PRD에 없음** — 본 문서의 가설. 확정되면 PRD에 역반영 |
