# Apple 디자인

Apple이 어떻게 컴퓨터처럼 느껴지지 않고 자신의 확장처럼 느껴지는 인터페이스를 만드는지에 대한 내용이다. 이 지식은 Apple의 WWDC 디자인 발표 — 주로 *Designing Fluid Interfaces*(WWDC 2018) — 에서 나왔으며, 웹 플랫폼(CSS, Pointer Events, `requestAnimationFrame`, Motion/Framer Motion 같은 스프링 라이브러리)에 맞게 정제되고 번역됐다.

핵심 맥락: **인터페이스는 모션이 현재 화면 값에서 시작하고, 사용자의 속도를 이어받고, 관성을 앞으로 투사하며, 언제든 붙잡혀 반전될 수 있을 때 살아있게 느껴진다.** 스프링은 본질적으로 중단 가능하고 속도를 인식하기 때문에 이 모든 걸 자연스럽게 만드는 도구다.

## 핵심 아이디어

> "인터페이스를 우리가 생각하고 움직이는 방식에 맞추면 마법 같은 일이 일어난다 — 컴퓨터처럼 느껴지지 않고 우리의 매끄러운 확장처럼 느껴지기 시작한다."

인터페이스는 물리적 세계처럼 행동할 때 유동적이다: 즉시 반응하고, 연속적으로 움직이고, 관성을 유지하고, 경계에서 저항하고, 움직이는 도중에도 방향을 바꿀 수 있다. 아래의 모든 내용은 거기에 더 가까이 다가가는 방법이다.

Apple은 디자인을 인간의 네 가지 욕구에 봉사하는 것으로 규정한다: **안전/예측 가능성, 이해, 성취, 그리고 기쁨.** 여기 있는 모든 규칙은 이 중 하나를 섬긴다.

## 1. 반응 — 지연을 없앤다

지연이 나타나는 순간, 직접적이라는 느낌은 "절벽에서 떨어지듯" 사라진다. 반응은 다른 모든 것이 세워지는 토대다.

- **떼는 순간이 아니라 누르는 순간에 반응한다.** 눌리는 즉시 버튼을 하이라이트한다. `click`/터치업까지 기다렸다가 피드백을 보여주면 죽은 느낌이 든다.
- **모든 지연에 예민하게 대응한다.** 디바운스, 인위적인 타이머, 트랜지션 대기, ~300ms 탭 지연을 감사한다. 입력 경로에서 필수적이지 않은 모든 것은 퇴보다.
- **피드백은 상호작용이 끝날 때만이 아니라 *진행되는 동안* 연속적이어야 한다.** 드래그, 슬라이더, 드로어의 경우 제스처 내내 포인터와 1:1로 UI를 업데이트한다 — 제스처가 끝났을 때만 애니메이션하지 않는다.

```css
/* 피드백은 누르는 순간에 살아있고, 즉각적이다 */
.button:active {
  transform: scale(0.97);
  transition: transform 100ms ease-out;
}
```

## 2. 직접 조작 — 1:1 트래킹

> "터치와 콘텐츠는 함께 움직여야 한다."

사용자가 뭔가를 드래그할 때, 그것은 손가락에 딱 붙어 있어야 하고 — *잡은 지점*으로부터의 오프셋을 존중해야 한다. 잡을 때 요소의 중앙으로 스냅되면 그 즉시 착각이 깨진다.

- 포인터가 요소 경계를 벗어나도 트래킹이 계속되도록 `setPointerCapture`와 함께 Pointer Events를 사용한다.
- 현재 지점뿐 아니라 짧은 **속도/위치 히스토리**(최근 몇 개의 `pointermove` 이벤트)를 추적한다 — 뗄 때의 속도가 필요하다.

```js
el.addEventListener('pointerdown', (e) => {
  el.setPointerCapture(e.pointerId);
  const grabOffset = e.clientY - el.getBoundingClientRect().top; // 어디를 잡았는지 존중
  // ...속도 계산을 위해 위치 + 타임스탬프 히스토리를 추적
});
```

## 3. 중단 가능성 — 가장 중요한 단일 원칙

> "생각과 제스처는 병렬로 일어난다."

모든 애니메이션은 언제든 중단되고 방향을 바꿀 수 있어야 한다. 사용자는 움직이는 요소를 도중에 붙잡아, 애니메이션이 끝나기를 기다리지 않고 반전시킬 수 있어야 한다. 사용자가 다시 붙잡은 닫히는 모달은 손가락을 따라가야 한다 — 먼저 닫힘을 끝낸 뒤 다시 여는 게 아니라.

- **트랜지션 도중 입력을 절대 잠그지 않는다.**
- **항상 목표값이 아니라 *현재 표시된* 값에서 애니메이션한다.** 중단됐을 때, 요소의 실시간 화면상 transform을 읽고 거기서 새 애니메이션을 시작한다. 논리적/목표 값에서 시작하면 눈에 띄는 점프가 생긴다.
- **제스처로 구동되는 것에는 CSS transition과 `@keyframes`를 피한다** — 도중에 부드럽게 붙잡고 반전시킬 수 없다. 스프링은 기본적으로 현재 값에서 애니메이션하는데, 이것이 정확히 중단이 필요로 하는 것이다.
- **제스처가 반전될 때는 속도를 하드컷하지 말고 블렌딩한다.** 반전 시점에 한 애니메이션을 다른 것으로 교체하면 속도 불연속, 즉 "벽돌 벽" 현상이 생긴다. 재조준 시 속도를 이어받는 스프링 라이브러리는 이를 피한다. (iOS의 *additive animations*가 네이티브로 하는 일이 바로 이것이다; 웹에서는 현재 속도에서 재조준하는 스프링 라이브러리를 선택한다.)
- **2D 모션을 독립적인 X, Y 스프링으로 분해한다.** 2D 거리에 스프링 하나를 쓰면 X와 Y의 속도가 다를 때 어긋난다.

## 4. 애니메이션이 아니라 행동 — 스프링을 쓴다

> "애니메이션을 인터페이스가 정해놓은 것이 아니라 당신과 대상 사이의 대화라고 생각하라."

미리 짜인 고정 지속시간 애니메이션은 새 입력에 반응할 수 없다. 스프링은 할 수 있다 — 새 입력은 그저 목표를 바꿀 뿐이고 모션은 계속 연속적이다. 사용자가 만질 수 있는 모든 것에는 스프링을 쓴다.

Apple은 물리학 삼총사(질량/강성/감쇠)를 의도적으로 디자이너 친화적인 두 파라미터로 대체했다. 이렇게 생각한다:

- **Damping ratio(감쇠비)** — 오버슈트를 제어한다. `1.0` = 임계 감쇠, 바운스 없음, 부드럽게 안정. `< 1.0` = 오버슈트하며 진동. 낮을수록 더 통통 튄다.
- **Response(반응성)** — 값이 목표에 도달하는 데 걸리는 시간(초). 낮을수록 더 경쾌하다. **이건 "지속시간"이 아니다** — 스프링은 고정된 지속시간이 없다; 안정 시간은 파라미터에서 나온다.

**기본값:**
- 대부분의 UI는 **damping `1.0`**(임계 감쇠)에서 시작한다 — 우아하고 산만하지 않다.
- 바운스(**damping ~`0.8`**)는 **제스처 자체가 관성을 실어 날랐을 때만** 추가한다(튕기기, 던지기, 드래그 놓기). 그냥 페이드인된 메뉴의 오버슈트는 이상하게 느껴지지만, 튕긴 카드의 오버슈트는 옳게 느껴진다.

**Apple이 실제로 쓰는 구체적인 값:**

| 상호작용 | Damping | Response |
| --- | --- | --- |
| 이동 / 재배치(예: PiP) | `1.0` | `0.4` |
| 회전 | `0.8` | `0.4` |
| 드로어 / 시트 | `0.8` | `0.3` |

**웹 매핑(Motion / Framer Motion):** `bounce` + `duration` 스프링 API가 Apple의 damping + response와 거의 일치한다. 안전한 하우스 스타일은 기본적으로 어디서나 `damping: 1.0` 스프링을 쓰고, 관성이 있는 물리적 상호작용에만 bounce를 아껴두는 것이다.

```js
import { animate } from 'motion';

// 임계 감쇠 기본값 (오버슈트 없음)
animate(el, { y: 0 }, { type: 'spring', bounce: 0, duration: 0.4 });

// 관성 상호작용 — 앞서 튕김이 있었기 때문에만 약간의 바운스
animate(el, { y: target }, { type: 'spring', bounce: 0.2, duration: 0.4 });
```

## 5. 속도 인계 — 드래그와 애니메이션 사이의 이음매

제스처가 끝나면 애니메이션은 **손가락의 정확한 속도로 이어져야** 하며, 그래야 드래그와 애니메이션 사이에 눈에 띄는 이음매가 생기지 않는다. 이것이 "유동적"과 "그럭저럭"을 가장 크게 갈라놓는 디테일이다.

포인터를 뗄 때의 속도를 스프링의 초기 속도로 전달한다. 일부 스프링 API는 **상대적** 속도를 원한다 — 목표까지 남은 거리로 정규화한다:

```
relativeVelocity = gestureVelocity / (targetValue − currentValue)
```

예: 요소가 `y=50`에, 목표가 `y=150`(100px 남음)에 있고, 손가락이 초당 50px로 움직인다 → 초기 스프링 속도 = `50 / 100 = 0.5`. Framer Motion / Motion은 절대 px/s 속도를 직접 받으므로(`velocity` 옵션), 보통은 원본 값을 그대로 넘기면 된다.

## 6. 관성 투사 — 제스처가 *향하는 곳*으로 애니메이션한다

> "작은 입력을 받아 큰 출력을 만들어라."

*뗀 지점*에서 가장 가까운 경계로 스냅하지 않는다. 스크롤 감속과 정확히 똑같이, 속도를 이용해 **정지 위치를 투사**한 뒤 그 투사된 지점에서 가장 가까운 목표로 스냅한다. 이것이 튕기는 동작을 요소를 던지는 것처럼 느껴지게 만드는 요소다.

Apple의 정확한 투사 함수(*Designing Fluid Interfaces* 샘플 코드에서):

```js
// 일반적인 스크롤 느낌엔 decelerationRate ≈ 0.998; 더 경쾌하게는 0.99
function project(initialVelocity /* px/s */, decelerationRate = 0.998) {
  return (initialVelocity / 1000) * decelerationRate / (1 - decelerationRate);
}

const projectedEndpoint = currentPosition + project(releaseVelocity);
const target = nearestSnapPoint(projectedEndpoint);   // 투사값에서 목표 선택
animateSpringTo(target, { velocity: releaseVelocity }); // 그다음 속도 인계 (§5)
```

참고: 물리 교과서식 `v²/(2·decel)`은 Apple이 실제로 쓰는 방식이 *아니다* — 위의 지수 감쇠 형태를 쓴다. 이것이 좋은 바텀시트와 캐러셀(Vaul, Embla)의 표준 동작이다.

## 7. 공간적 일관성 — 대칭 경로, 고정된 원점

> "무언가가 한 방향으로 사라지면, 우리는 그것이 왔던 곳에서 나타나기를 기대한다."

- **같은 경로로 진입하고 퇴장한다.** 오른쪽에서 슬라이드해 들어온 패널은 오른쪽으로 닫혀야 한다. 오른쪽에서 들어와 아래로 나가면 단절되고 헷갈리게 느껴진다.
- **상호작용을 그 근원에 고정한다.** 메뉴, 팝오버, 시트는 그것을 트리거한 요소에서 시작해야 한다 — `transform-origin`을 트리거로 설정해서 버튼과 콘텐츠 사이의 공간적 관계를 명확히 한다. (팝오버가 자기 중앙이 아니라 트리거에서 scale되는 것과 같은 원점 인식 포인트다.)
- **반전 가능한 트랜지션의 easing을 미러링한다** 그래서 나가는 경로가 돌아오는 경로와 일치하도록 한다(두 방향에 서로 역인 cubic-bezier 제어점을 사용).

## 8. 제스처 방향으로 힌트를 준다

인간은 궤적으로부터 최종 상태를 예측한다. 중간 모션은 사물이 어디로 향하는지를 신호해야 한다 — 컨트롤 센터 모듈은 "손가락을 향해 위로, 밖으로 자란다." 중간 프레임이 결과를 그냥 무심코 보간하는 게 아니라 결과를 가리키게 만든다.

## 9. 러버밴딩 — 부드러운 경계

경계에서는 딱딱하게 멈추는 대신 점진적으로 저항한다. 딱딱한 정지는 "멈췄다"로 읽히고, 연속적인 저항은 "반응하지만 여기서 더는 없다"로 읽힌다. 사용자가 경계를 더 멀리 드래그할수록 커지는 감쇠를 적용한다.

```js
// 경계를 넘을수록 요소는 덜 따라간다 — 실제 사물은 멈추기 전에 느려진다
function rubberband(overshoot, dimension, constant = 0.55) {
  return (overshoot * dimension * constant) / (dimension + constant * Math.abs(overshoot));
}
```

## 10. 제스처 디자인 디테일("느낌" 체크리스트)

- **탭:** 터치가 *시작될 때*(즉시) 하이라이트하고, 터치가 *끝날 때* 커밋한다. 대상 주변에 ~10px의 히스테리시스/히트 패딩을 추가하고, 드래그해서 벗어나 취소하고 돌아오는 것을 허용한다.
- **드래그/스와이프:** 방향을 커밋하기 전에 작은 이동 임계값(히스테리시스, ~10px)을 요구한 뒤 1:1로 추적한다.
- **첫 움직임부터 가능한 모든 제스처를 병렬로 감지**한 뒤, 의도가 명확해지면 자신 있게 패자를 취소한다. *최종* 상태만 보고하는 인식기(`swipeleft` 유형 이벤트)는 피한다 — 피드백에 필요한 연속적인 추적을 버리기 때문이다.
- **모호성 해소 지연을 최소화한다.** 더블탭 감지는 불가피하게 단일 탭을 지연시킨다; 더블탭이 실제로 존재하는 곳에서만 그 비용을 치른다.

## 11. 프레임 단위의 부드러움

부드러움은 프레임 레이트만이 아니라 *프레임 안에 무엇이 있는지*에 관한 것이다.

- 스트로빙을 피하기 위해 프레임당 위치 변화량을 지각 임계값 아래로 유지한다.
- 매우 빠른 모션에는 미묘한 **모션 블러/스트레치**가 속도를 표현하며, 딱딱하고 선명한 궤적보다 더 잘 읽힌다.
- `requestAnimationFrame`은 웹의 디스플레이 동기화 시계다(Apple은 `CADisplayLink`를 사용). 컴포지터 친화적인 속성 — `transform`과 `opacity` — 만 애니메이션하고, 모션이 임박한 곳에는 `will-change`로 힌트를 준다.

## 12. 재질과 깊이 — 반투명성이 위계를 전달한다

Apple은 반투명 재질을 초점을 뺏지 않으면서 구조를 부여하는 떠 있는 기능적 레이어로 사용한다. 웹에서는 `backdrop-filter`로 근사한다.

- **내비게이션/툴바/시트를 반투명 레이어로 만든다**(`backdrop-filter: blur()` + 반투명 배경)와 콘텐츠는 그 아래로 스크롤된다 — 고정된 띠를 차지하는 불투명 바가 아니다.
- **재질의 무게가 위계를 표현한다:** 더 어둡고/무거운 재질은 구조적 영역(사이드바)을 분리한다; 더 가벼운 재질은 상호작용 요소(버튼)에 시선을 끈다. **밝은 반투명 표면을 다른 반투명 표면 위에 절대 쌓지 않는다** — 가독성이 무너진다.
- **더 큰 표면은 더 두껍게 읽혀야 한다:** 작은 칩보다 강한 블러 + 더 깊은 그림자. 맥락 인식 그림자를 고려한다 — 분리를 위해 바쁜/텍스트 콘텐츠 위에서는 더 무겁게, 단순한 배경 위에서는 더 가볍게.
- **초점을 위해 어둡게, 흐름을 유지하려면 분리한다.** 모달 작업은 표면에 어둡게 하는 스크림을 짝지어 배경을 뒤/아래로 밀어낸다. 병렬적이고 막지 않는 패널은 흐름을 깨지 않도록 스크림 *없이* 반투명성과 오프셋을 쓴다. 겹쳐진 시트의 경우 부모 레이어를 점진적으로 어둡게 하고 뒤로 민다.
- **Vibrancy가 변하는 배경 위에서도 텍스트를 읽기 쉽게 유지한다.** 흐려진/반투명 표면 위에서는 밋밋한 회색 텍스트를 쓰지 않는다 — 더 높은 대비, 살짝 더 무거운 굵기, 작은 자간 증가를 쓴다. 색상은 반투명 전경이 아니라 불투명 레이어에 둔다.
- **하드 디바이더가 아니라 스크롤 엣지 효과.** 고정 헤더 아래 1px 테두리 대신, 떠 있는 크롬이 콘텐츠와 실제로 겹치는 곳에서만 작은 블러/그라디언트 마스크로 페이드시킨다.
- **그냥 페이드가 아니라 물질화시킨다.** 유리/블러 표면의 경우, 진입/퇴장 시 blur 반경과 scale을 함께 애니메이션해서 단순한 opacity 페이드가 아니라 실제 재질이 도착하는 것처럼 읽히게 한다.

```css
.toolbar {
  background: rgba(255, 255, 255, 0.6);
  backdrop-filter: blur(20px) saturate(180%);
  border-top: 1px solid rgba(255, 255, 255, 0.4); /* 밝은 상단 가장자리 = 재질에 빛이 닿는 느낌 */
}
```

## 13. 다중 감각 피드백 — 모션 + 사운드 + 햅틱

감각을 조합하는 세 가지 규칙(*Designing Audio-Haptic Experiences*에서):

1. **인과성** — 무엇이 피드백을 유발했는지 명확해야 한다. 실제 원인이 되는 이벤트(토글이 뒤집히는 순간, 항목이 제자리로 스냅되는 순간)에서 발화시키고, 그 성격을 액션의 물리적 특성에 맞춘다.
2. **조화** — 시각, 소리, 햅틱은 **같은 프레임**에서 발화해야 한다. 이들 사이의 지연은 착각을 무너뜨린다. CSS 트랜지션이 오디오/햅틱(Vibration API)보다 지연되게 두지 않는다.
3. **효용** — 제자리를 벌 수 있는 곳에만 피드백을 추가한다. 햅틱/사운드는 의미 있는 순간(성공, 오류, 커밋, 스냅)에 아껴둔다. 과도한 피드백은 사용자가 그것을 전부 무시하도록 훈련시킨다.

## 14. Reduced motion과 접근성

Reduced motion은 피드백이 *없다*는 뜻이 아니다 — 더 부드럽고, 전정 감각을 자극하지 않는 등가물을 뜻한다. 세 가지 독립적인 신호에 반응하고 컴포넌트에 녹여 넣는다:

- **`prefers-reduced-motion: reduce`** — 슬라이드/스프링/패럴랙스를 짧은 opacity **크로스페이드나 정적 트랜지션**으로 대체한다. 탄성/오버슈트는 제거한다. 이해를 돕는 opacity/색상 변화는 유지한다.
- **`prefers-reduced-transparency: reduce`** — 반투명 표면을 더 서리 낀/불투명하게 만든다: 배경 불투명도를 높이고 블러를 뺀다.
- **`prefers-contrast: more`** — 명확하고 대비되는 테두리를 가진 거의 불투명한 배경.

또한: 전체 뷰포트를 움직이는 배경, 느린 반복 진동(초당 약 0.2Hz, 즉 5초에 한 사이클), 갑작스러운 밝기 점프(다크↔라이트 테마 전환은 부드럽게)를 피한다. 크게 움직이는 객체는 이동하는 동안 반투명하게 만들고, 큰 재배치 동안에는 큰 표면을 페이드아웃했다가 안정된 후 다시 페이드인한다.

```css
@media (prefers-reduced-motion: reduce) {
  .sheet { transition: opacity 200ms ease; transform: none !important; }
}
@media (prefers-reduced-transparency: reduce) {
  .toolbar { background: white; backdrop-filter: none; }
}
```

## 15. 타이포그래피 — 광학 크기, 자간, 행간

Apple은 크기에 따라 형태가 바뀌도록 활자를 디자인한다; 같은 원칙이 웹에도 적용된다. (*The Details of UI Typography*, WWDC 2020에서.)

- **자간(letter-spacing)은 크기별로 달라야 하며 — 모든 크기에 하나의 값을 쓰면 안 된다.** 큰 디스플레이 텍스트는 *음수* 자간을 원한다(글자가 커질수록 너무 멀어져 보인다); 작은 텍스트는 가독성을 위해 약간 *양수* 자간을 원한다. 고정된 `letter-spacing`은 어딘가에서는 틀리다. 제목은 좁히고, 본문은 `0`에 가깝게 둔다.
- **행간(line-height)은 크기와 반비례한다.** 큰 제목에서는 좁게, 본문 카피에서는 더 느슨하게. 위아래로 긴 획을 가진 문자 체계에는 늘리고, 정보 밀도가 높은 UI에는 좁힌다.
- **위계는 크기 하나가 아니라 굵기 + 크기 + 행간을 하나의 세트로 구축한다.** 굵기로 강조한다 — 공간을 더 차지하지 않으면서 존재감을 더한다.
- **사용자의 텍스트 크기 설정을 존중한다**(Dynamic Type). 레이아웃을 텍스트와 *함께* 스케일한다 — 고정 px가 아니라 `rem`/`em` 단위 간격 — 그래야 큰 폰트가 레이아웃을 깨지 않는다.
- **커스텀 서체보다 플랫폼의 시스템 폰트를 기본값으로 쓴다**; 이미 광학 크기 조정, 자간 표, 가독성 튜닝이 내장되어 있다. 이유가 있을 때만 오버라이드한다.

```css
:root { font: 100%/1.5 system-ui, sans-serif; } /* 본문: 시스템 폰트, 편안한 행간 */

.display {
  font-size: clamp(2rem, 5vw, 4rem);
  line-height: 1.05;        /* 큰 텍스트를 위한 좁은 행간 */
  letter-spacing: -0.02em;  /* 커질수록 음수 자간 */
  font-optical-sizing: auto;
}
```

## 16. 디자인 기초 — 여덟 가지 원칙

위의 모션과 완성도는 Apple의 여덟 가지 디자인 원칙(*Principles of Great Design*, WWDC 2026)을 섬긴다. 이것들을 판단의 근거로 삼는 이름으로 사용한다:

1. **목적(Purpose).** 의도를 갖고 만든다; 무엇을 *만들지 않을지* 결정한다. 모든 기능은 사용자의 시간, 주의, 신뢰를 요구한다 — 그 예산은 갚을 가치가 있는 곳에만 쓴다.
2. **주체성(Agency).** 사람들을 통제권 안에 둔다: 선택지를 제공하고, 단일 경로를 강요하지 않는다. 관용으로 뒷받침한다 — 실수에는 쉬운 실행 취소를, 진짜로 파괴적이고 되돌릴 수 없는 액션에만 확인 대화상자를(아껴 쓴다 — 남용하면 사람들이 그냥 클릭해서 넘기도록 훈련된다).
3. **책임(Responsibility).** 사용자의 이익을 위해 행동한다. 프라이버시: 적절한 순간에, 필요한 것만, 투명하게 묻는다. 안전: 특히 AI와 관련해 오용과 해악을 미리 예상한다(알레르기를 고려하는 레시피 앱은 유해한 재료를 제안해서는 안 된다). 미리보기, 확인, 면책 조항을 추가한다; 위험이 가치를 넘어서는 기능은 잘라낸다.
4. **친숙함(Familiarity).** 사람들이 이미 아는 것 위에 짓는다. 너무 문자적이지도, 너무 추상적이지도 않은 은유를 쓰고(휴지통은 삭제를 의미한다), 그 물리 법칙을 존중한다. 일관되게: 똑같아 보이는 것은 똑같이 동작해야 하고 같은 자리에 있어야 한다(macOS에서 닫기는 항상 왼쪽 위) — 그래야 사람들이 다음에 무슨 일이 일어날지 예측할 수 있다. 친숙한 패턴은 더 낫다는 걸 증명할 수 있을 때만 깬다 — 그런 다음 테스트한다, 가정하지 않는다.
5. **유연성(Flexibility).** 다양한 맥락, 기기, 그리고 능력 전체 범위를 위해 디자인한다. 플랫폼(아이폰 = 빠른 터치; 데스크톱 = 정밀한 포인터 제어를 갖춘 깊은 워크플로)과 상황에 적응한다. 포용적으로 디자인한다(연령, 언어, 전문성, 접근성). 모두에게 맞는 단일 레이아웃이 없다면 사람들이 개인화하게 한다 — 컨트롤을 재배치하고, 쓰지 않는 것을 숨기게.
6. **단순함(Simplicity) — 미니멀리즘이 아니다.** 핵심 목적이 빛나도록 불필요한 것을 걷어낸다; 모든 걸 한 곳에 묻어두면 미니멀해 보이지만 단순하지는 않다. 간결하게(평이한 언어, 전문용어 없이, 더 적은 단계) 그리고 명확하게(위계를 사용한다 — 순서, 간격, 대비 — 가장 중요한 것이 가장 눈에 띄도록). 모든 요소는 자기 자리를 벌어야 한다; 때로는 맥락을 *더하는 것*이 단순화다(남은 시간을 보여주는 비디오 스크러버). 흔한 경로를 먼저 보여주고, 고급 옵션은 한 단계 더 깊이 둔다.
7. **완성도(Craft).** 타협 없는 디테일에 대한 관심이 신뢰를 쌓는다. 아름다운 타이포그래피, 라이트/다크에 적응하는 색상, 명확한 아이콘, 즉각적이고 자연스러운 피드백을 주는 반응형 애니메이션. 아무것도 무작위가 아니다 — 모든 간격, 타이밍, 정렬 값은 변호할 수 있는 의도적인 선택이다. 흔들리는 스크롤, 정렬이 어긋난 아이콘, 회전 시 깨지는 레이아웃은 부주의로 읽힌다. 완성도에는 반복과 지속성이 필요하다 — 기능과 하드웨어가 변함에 따라 디자인을 계속 진화시킨다.
8. **기쁨(Delight).** 다른 일곱 가지를 제대로 했을 때의 결과이지, 위에 얹은 색종이가 아니다. 사람들이 느끼길 바라는 감정(차분함, 자신감, 설렘)을 정하고 모든 결정에서 그것을 강화한다.

이를 뒷받침하는 전술적 규칙:

- **피드백은 네 가지 종류다:** 상태, 완료, 경고, 오류. 의미 있는 액션은 확인하고, 진행 중인 상태를 노출하고, 문제 전에 경고하고, 제출 시가 아니라 인라인으로 검증한다.
- **길찾기(Wayfinding).** 모든 화면은 답해야 한다: 나는 어디에 있나? 어디로 갈 수 있나? 거기엔 뭐가 있나? 어떻게 나가나? 사용자를 절대 가두지 않는다.
- **그룹화 & 매핑.** 근접성은 관계를 암시한다; 컨트롤을 그것이 영향을 미치는 것 근처에 두고, 컨트롤 배치가 그것이 바꾸는 것을 반영하게 한다. 컨트롤을 설명할 라벨이 필요하다면 매핑이 약한 것이다.
- **직접적이고 구체적인 라벨이 안전하고 일반적인 라벨보다 낫다.** 내비게이션 항목의 이름은 모호한 포괄어("홈")가 아니라 그 콘텐츠에 맞게("진행 상황", "라이브러리") 짓는다. 구체성이 예측 가능성을 만든다.

## 17. 프로세스

- **인터랙티브하게 프로토타입한다 — 인터랙티브 데모 하나가 "정적 디자인 백만 개"의 가치를 갖는다.** 인터페이스는 만들고 가지고 놀아보면서 발견한다; 동작하는 프로토타입은 또한 평범한 최종 구현을 막는 구체적인 기준을 세운다.
- **상호작용과 비주얼을 함께 디자인한다.** "어디서 하나가 끝나고 다른 하나가 시작되는지 구별할 수 없어야 한다." 모션은 픽셀 위에 나중에 얹는 레이어가 아니다.
- **실제 사람들과 실제 맥락에서 테스트하고**, 새로운 눈으로 모션을 리뷰한다 — 전체 속도에서는 보이지 않는 것을 잡기 위해 슬로우 모션/프레임 단위로 재생한다.

## 빠른 참조

| 필요 | 기법 | 구체적인 값 |
| --- | --- | --- |
| 기본 UI 스프링 | 임계 감쇠, 오버슈트 없음 | `damping 1.0`, `response 0.3–0.4` |
| 관성/튕김 스프링 | 저감쇠, 약간의 바운스 | `damping ~0.8`, `response 0.3–0.4` |
| 제스처 → 스프링 속도 | 뗄 때의 속도 인계 | 정규화한다면 `gestureVelocity / (target − current)` |
| 튕김 착지 지점 | 관성 투사 | `current + (v/1000)·d/(1−d)`, `d ≈ 0.998` |
| 깔끔하게 중단하기 | 표시된(실시간) 값에서 시작 | 화면상 transform을 읽음 |
| 반전 "벽돌 벽" 피하기 | 재조준 시 속도를 이어받음 | 속도를 블렌딩하는 스프링 |
